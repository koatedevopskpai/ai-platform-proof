# O03: rollback and provider-failure/fallback drill

The application now returns explicit `generation_mode` and `fallback_reason`
metadata. HTTP provider failures, transport failures and invalid/empty responses
produce a deterministic source-based fallback with a bounded reason code; raw
provider error bodies are not returned. Existing guardrail/source behaviour is
retained. The supported release profile remains synthetic mock mode.

## Two separate incidents

The first drill builds and accepts a known-good immutable release via O02. It
then deliberately installs the controlled wrong-answer image directly, bypassing
the normal gate only inside the incident simulation. This represents a runtime
regression after release, not the normal promotion procedure. Actual gateway
responses fail the same three acceptance cases. The operator restores the saved
last known-good bundle through the normal release CLI; candidate checks and
post-promotion functional acceptance must pass, and running image IDs must match
the saved good IDs. The known-good bundle is selected explicitly by the operator,
not discovered by an automated release-history/rollback controller.

The second drill leaves the good application image intact and changes generation
configuration to an isolated HTTP provider simulator that returns 503. Its test
key is synthetic; no external model request is made. Actual gateway requests
exercise the application's provider error handler. Four failed provider requests
are counted by the simulator: one detection request and three acceptance cases.
All three fallback answers must retain fixture facts and source IDs, and report
`provider_http_503`. An HTTP 200 alone cannot establish fallback acceptance.

The operator then restores the known-good bundle/configuration, again requiring
the normal release gate and functional smoke. This removes the simulated provider
configuration and returns to `mock_generation`; it does not prove that a real
provider recovered or that automatic live-provider failback works.

## Reproduction and operator sequence

From a clean Linux checkout with Docker/Compose and ports 3002/3003 available:

```sh
python -m unittest discover -s tests -v
pip install -r services/rag-api/requirements-dev.txt
python -m pytest services/rag-api/tests -q
python tests/integration_o03.py
```

The drill performs: accept baseline -> install controlled application fault ->
detect via actual responses -> restore last known-good bundle -> inject HTTP 503
provider -> detect explicit fallback -> compare the three acceptance cases ->
restore known-good configuration. Each incident JSON records UTC trigger,
detection and recovery times, monotonic elapsed seconds, operator steps and
restored image IDs. Reports bind actual responses to the correct good/fault
image IDs, source/manifest and changed configuration. The provider's request
counter independently confirms that the failure path was exercised.

After a local reproduction, remove the synthetic stack and its local data:

```sh
docker compose -p o03-smoke -f artifacts/O03-integration/baseline/compose.json down --volumes --remove-orphans
```

The simulator is removed in the drill's finally block. The bounded cloud harness
also terminates its task-only EC2 host and verifies disk/key/security-group
deletion. No shared VPC/subnet is deleted. The task private SSH key stays in memory.

## Timing and scope limits

Detection time starts immediately before the fault/configuration apply command
and ends when failed-answer/fallback checks detect the condition. It includes
container reconfiguration, not just monitor sampling delay. Recovery time starts
at the operator's restore command and ends after release acceptance and image
verification. Each is one synthetic run, not an SLO, sustained uptime measure,
zero-downtime promise or representative production incident distribution.

Fallback is deterministic extraction from retrieved sources, not an alternative
LLM provider. The three self-authored cases do not establish semantic reliability,
abstention behaviour on unknown questions or faithful answers across a corpus.
O02's unsigned-manifest/trusted-runner and mock-profile boundaries still apply.
O04 incident telemetry and alerting remain a separate task; B01 is deferred.
