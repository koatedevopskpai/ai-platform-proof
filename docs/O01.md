# O01: one immutable Compose release path

The supported release is EC2/Linux + Docker Compose. Kubernetes/Helm remains
unvalidated design material; the old EKS workflow no longer deploys automatically
and fails explicitly when manually invoked. The previous source-based deployment
ignored `git pull` failures. Both that script and bootstrap application deployment
have been removed from the supported path.

## Build and deployment contract

A clean Git checkout builds three application images, each labelled with the
full source commit. The build resolves those images and PostgreSQL to immutable
local Docker image IDs and saves them in one image archive. The manifest records
those IDs, source revision, build time, execution mode and SHA-256 checksums for
the archive and the exact Compose configuration. The gateway uses `npm ci`.

The build can resolve mutable base tags or dependencies: this is build-once,
deploy-that-artifact reproducibility, not a claim of bit-identical rebuilds.
Local image IDs identify immutable image configuration/rootfs content; they are
not registry manifest digests or a signed supply-chain attestation. No registry
is needed for this small demonstration. The operator must trust the runner,
manifest, expected revision and transport; checksums are not authentication.

Deployment rejects wrong source, changed bytes, mutable image references or
inconsistent Compose image IDs before loading/starting anything. It loads the
archive, checks application source labels, starts with `--no-build --pull never`,
and verifies actual running image IDs. The receipt records source, expected and
running images, configuration/manifest hashes, health result and timestamps.
Failures after preflight produce a failed receipt and nonzero exit; they never
print unconditional deployment success. A receipt file cannot be overwritten.

Health must include two healthy backend payloads, not merely HTTP 200 from the
gateway. The gateway now reads each backend's JSON status as well as HTTP status.
This closes the degraded-backend HTTP-200 false pass. O01 health is connectivity
evidence only; real application requests and quality gating belong to O02.

The generated release configuration has synthetic credentials, mock embeddings,
no model keys, no public database/backend ports and a gateway bound to loopback.
It is a demonstration profile, unsuitable for confidential data or public access.
Use a verified SSH tunnel. The GitHub workflow requires a pinned known_hosts
secret; it does not trust an unauthenticated keyscan or disable host checking.

## Commands

```sh
python -m unittest discover -s tests -v
python scripts/release/release.py build --out /tmp/release
python scripts/release/release.py deploy --bundle /tmp/release --expected-source <commit> --receipt /tmp/receipt.json
docker compose -p ai-platform -f /tmp/release/compose.json down --volumes
```

The last command deletes the synthetic local demo data. Choose the same project
name used for deployment. Do not apply it to another deployment's volumes.
Host preparation is separate from release deployment; Terraform bootstrap no
longer starts an application from a mutable source checkout. Existing EKS/RDS
infrastructure files are not a supported deployment path.

## Scope and remaining tasks

O02 must attach meaningful candidate evaluation and real gateway requests before
promotion. O03 must demonstrate rollback/fallback; O04 must demonstrate useful
incident traces, alerts and load behaviour. This change does not establish those
capabilities, production readiness, security certification or sustained uptime.
No GitHub workflow execution or publishing is implied by local/Linux validation.

## Observed validation — 17 October 2026

Live tested source: `5b40eaca0cfa9fa902af11079304e6c15429d70f`. The final handoff commit adds documentation
and evidence only. The host was Amazon Linux 2023 x86_64; release contracts ran
in `python:3.12-slim`, gateway CI in `node:22-alpine`, and the actual build/deploy
orchestrator ran with host Python 3.9. Four release tests and two gateway tests
passed on Linux. `npm ci`, typecheck and compilation all passed. The images built,
deployed and redeployed from the same archive successfully; both receipts reported
healthy gateway backends and exact expected/running image equality.

This ran directly on a temporary EC2 host, not through GitHub Actions, and did
not validate transfer between two hosts or the GitHub secrets/environment setup.
The exact CI release-test command and gateway install/build/test commands ran
on Linux. Full unchanged Python/evaluator/.NET CI suites were not run as part of
O01; all three runtime application images did build and start. Mock mode was
explicit, with no provider calls. Quality gate behaviour is deferred to O02.

Temporary EC2 instances and disks, task SSH key pairs and security groups were
deleted and absence verified, including the failed attempts. First launch was
rejected because the account restricts instance types to Free Tier eligibility;
the second attempt failed because the initial harness did not select the bundle's
task branch. The corrected harness explicitly selects it. Both failures and
cleanup receipts are retained, without being presented as successful deployments.

AWS pricing API returned USD 0.11072/hour for Linux m7i-flex.large in London,
effective 2026-10-01. Using the entire orchestration interval as an upper bound
on compute runtime gives USD 0.010167 for the two launched instances. That
excludes EBS/public IPv4/networking/tax and credits; actual billing remains
unreconciled. Each sequential attempt had a USD 1 allowance within the shared
USD 10 ceiling; these allowances are not actual spend. Instances had 35 GB gp3
DeleteOnTermination disks and a 115-minute shutdown that terminates the host.

Teardown performed by the harness, scoped to its own recorded IDs:

```sh
aws ec2 terminate-instances --instance-ids <task-instance> --region eu-west-2
aws ec2 describe-instances --instance-ids <task-instance> --region eu-west-2
aws ec2 describe-volumes --filters Name=volume-id,Values=<task-volume> --region eu-west-2
aws ec2 delete-key-pair --key-name <task-key> --region eu-west-2
aws ec2 delete-security-group --group-id <task-group> --region eu-west-2
```

Only the existing default VPC/subnet was reused. No shared resource was deleted.
SSH server keys were checked against fingerprints obtained from authenticated
EC2 console output. The task private key existed only in process memory.
