# O02: evaluate the candidate application before promotion

The release no longer treats stored dataset answers as application evidence. The
legacy evaluator workflow is replaced with offline contract checks; actual HTTP
acceptance is mandatory inside the immutable Compose release, before promotion.
No model key is required, and mock execution is labelled explicitly throughout.

## Evaluation and provenance

The release bundles and hashes its dataset, evaluator, gate implementation and
policy. It checks the executed evaluator/gate bytes against the manifest and
loads the dataset before Docker operations. A missing, empty or invalid dataset
cannot pass. Every deployment performs fresh evaluation inline; there is no CLI
option to promote using a saved quality report.

The candidate uses the exact application image IDs that will be promoted, with
an isolated database volume and a loopback gateway on port 3003. Its configuration
is derived from the release configuration by changing only the gateway port.
The report records both configuration hashes, dataset hash, source commit,
manifest hash, expected/running images and a unique deployment run identifier.
The image IDs are checked before and after evaluation and again after promotion.
This follows R01's candidate-provenance principles, not its Azure-specific judge.

Three synthetic documents are ingested through the gateway and .NET service.
Each case calls the running gateway's `/search` and `/rag` endpoints. The scored
answer comes from the application; the dataset contains fixture facts and
acceptance predicates, not stored answer strings to score in place of generation.
The cases cover a 30-day refund window, opened software not refundable and a
GBP 25 meal limit. Responses must include the required fixture phrases, exclude
forbidden phrases, expose actual known source IDs and matching retrieved source
bytes, and explicitly report deterministic fallback behaviour.

The E04 `gate_policy.py` is reused unchanged, with upstream commit/hash documented
in scripts/release/UPSTREAM.md. It rejects missing context/answers, nonfinite or
missing scores, invalid citations, evaluator errors and per-case/mean failures.
O02 scores are binary fixture predicates, not LLM faithfulness/relevance scores
or semantic entailment. Its policy requires every predicate to pass (floors 1).
E04's model-score calibration is not transferred to this different score scale.
Token/source existence checks can miss semantic contradictions and irrelevant
extra text. No broad answer-quality, retrieval-quality or model-quality claim is
supported by this three-case development fixture. B01 stays deferred.

Candidate containers/volumes are removed before promotion is permitted. A failed
candidate leaves the active application untouched. After promotion, the same
functional checks run through port 3002 against the actual promoted stack.
Post-promotion failure produces a failed receipt; automatic recovery is not
implemented by O02 (O03 supplies a separate recovery drill). The simple runner
supports one release at a time; the GitHub workflow serialises releases.

## Controlled negative candidate

The drill builds a different RAG image containing an explicitly wrong application
implementation. The real gateway receives and returns its wrong answers; the
evaluation harness does not replace answers. The derivative image records its
source revision, controlled-fault label and fixture hash. It uses a local
source-revision tag only after checking its immutable parent image ID. Deployment
and reporting still use image IDs. This is a controlled drill, not another
commercial incident or a separately committed application regression.

The drill requires the bad candidate to fail before promotion and verifies that
the active image IDs still match the accepted baseline. It then physically
removes the acceptance dataset and requires another pre-promotion failure, again
checking the active images. It records those results rather than merely asserting
that the gate code looks correct. Source code and threshold policy are unchanged
between the baseline and bad-answer evaluation.

## Reproduction

From a clean checkout on Linux with Docker/Compose, enough build disk space and
loopback ports 3002/3003 free:

```sh
python -m unittest discover -s tests -v
python tests/integration_o02.py
```

Generated receipts, reports, image archives and logs live in artifacts/O02-integration
and remain ignored by Git. The second command creates a local synthetic stack;
remove it with the exact project/configuration it created:

```sh
docker compose -p o02-smoke -f artifacts/O02-integration/baseline/compose.json down --volumes --remove-orphans
```

The cloud lifecycle harness additionally terminates its dedicated EC2 host and
deletes its disk, SSH key and security group in the same session. Only the
pre-existing default VPC/subnet is reused. No paid model requests are made.
The release fixes PostgreSQL vector parameter binding with an explicit vector
cast; this route is exercised by actual HTTP search/RAG in the drill.

## Limits

This proves a small synthetic mock release contract. It does not establish live
LLM quality, production data behaviour, held-out generalisation, uninterrupted
availability, automatic rollback or cross-host/GitHub workflow execution. The
manifest/runner/transport must be trusted; unsigned checksums are not identity or
security attestation. Mutable build inputs and O01's other limits remain.
